# 俄罗斯方块架构文档

## 1. 文档目的
本文档只定义项目的架构边界、模块职责和数据流，不记录具体代码实现细节。  
实现细节请查看 `实现文档.md`。

---

## 2. 架构风格（适合当前项目）
当前项目建议采用 **轻量分层架构（Gameplay Core + Unity Adapter）**：

- **Gameplay Core（纯逻辑层）**  
  不依赖 `MonoBehaviour`，只处理棋盘状态、规则判断、碰撞、消行、得分等。
- **Unity Adapter（引擎适配层）**  
  由 `Game` 等 `MonoBehaviour` 组成，负责生命周期、输入采集、时间驱动、UI/Prefab 渲染。

这样做的好处：
- 逻辑和表现解耦，后续改 UI 不会影响核心规则。
- 规则层更容易测试和调试。
- 对新手友好：先在 `Game` 驱动，再逐步把逻辑沉淀到纯 C# 类中。

---

## 3. 分层与职责

### 3.1 入口层（Application）
- **Game（入口编排）**
  - 管理游戏主循环（Tick/Drop）。
  - 协调棋盘逻辑层和渲染层。
  - 处理暂停、重开、结束状态切换。

### 3.2 领域层（Domain / Core）
- **ChessBoard（棋盘聚合根）**
  - 保存棋盘占用数据（如 `cells`）。
  - 提供规则能力：能否移动、落地、锁定、消行、是否游戏结束。
  - 对外暴露“意图式”方法（如 TryMove/LockPiece），而不是让外部直接改数组。

- **Piece / Cell 数据模型（建议）**
  - `Piece`：当前活动方块的形状、旋转状态、基准坐标。
  - `Cell`：建议作为数据结构或渲染单位，不再承担棋盘全局状态。

### 3.3 表现层（Presentation）
- 方块实例化、位置映射、动画和特效。
- UI（分数、等级、暂停、结算）。

### 3.4 基础设施层（Infrastructure，可后续补）
- 配置（棋盘尺寸、下落间隔、得分规则）。
- 存档（最高分、本地设置）。
- 日志和调试开关。

---

## 4. 关键设计原则

1. **单一数据源（Single Source of Truth）**  
   棋盘占用状态只能由 `ChessBoard` 维护，避免在多个类中重复保存。

2. **逻辑坐标优先**  
   先更新逻辑坐标，再映射到 UI 坐标；不要直接用 UI 坐标驱动游戏规则。

3. **规则封装**  
   外部不要直接写 `cells[x,y]`，统一通过棋盘方法调用，降低后续改动成本。

4. **显式状态机（建议）**  
   游戏状态至少包含：`Init` / `Running` / `Paused` / `GameOver`。

---

## 5. 推荐数据流

1. 输入层收到操作（左右移、旋转、加速下落）。  
2. `Game` 将操作意图转发给 `ChessBoard`。  
3. `ChessBoard` 执行规则判断并更新逻辑状态。  
4. `Game` 读取最新状态并驱动渲染层刷新。  
5. 若发生落地/消行/结束，触发对应事件给 UI 层。

---

## 6. 模块边界（避免重复）

- `Game`：只做“调度与驱动”，不持有复杂规则判断。
- `ChessBoard`：只做“规则与状态”，不关心 Unity 组件细节。
- `Cell`：仅保留单格语义（若保留为组件），不再维护整盘 `cells`。

---

## 7. 单例策略建议

你提到 `ChessBoard` 后续准备做单例，这在单局游戏中是可行的。  
但从可维护性看，推荐优先级如下：

1. **优先：由 `Game` 持有实例并注入依赖**（更容易测试、切关卡）。  
2. **可选：`ChessBoard` 单例**（简单直观，但扩展多人模式/回放时受限）。

如果使用单例，需明确初始化时机，确保宽高和网格只初始化一次且可重置。

---

## 8. 后续演进路线（架构视角）

1. 完成最小闭环：下落 -> 碰撞 -> 落地 -> 生成新方块。  
2. 引入方块形状与旋转系统。  
3. 引入消行与得分。  
4. 接入状态机和 UI 事件流。  
5. 抽离配置与测试，形成稳定核心层。

---

## 9. 非目标（本阶段不做）
- 网络对战、多线程物理优化、复杂特效系统。  
- 过早拆分过多服务类，先保证核心规则稳定。
